# Audit — 2026-10-07 — claude-opus-5-5

This is a read-only audit of `master` at `abb11fb`, 52 commits after the 2026-09-23 baseline at `b1a220a`. Four `opus-scout` subagents covered four dimensions: core correctness, security and privacy, interface with a states sweep, and process and docs. The orchestrator opened the cited lines for every High and every finding that leads a section. Anything not opened is marked plausible.

- **Repo:** `ShortFlip/squares`, **public** on GitHub.
- **Size:** about 22,300 tracked lines in code, SQL and config. Roughly 20,000 of them are under `src/`.
- **Health:** `vitest` passes 277/277 tests across 24 files. `tsc --noEmit` and lint are both clean. `npm audit --omit=dev` reports 2 high advisories and nothing else: sharp below 0.35.5, and source-map-js. `npm audit fix` clears both. The baseline had 18 advisories, including 1 critical.
- **Secrets:** none in the tree or in git history. The only env file ever added is `.env.mock`, and its JWT is a fake mock-supabase token.
- **Open issues:** #1, "verify-bingo edge function is dead code; client writes won:true directly". Findings below that belong to it are marked.

The audit measured the code against DESIGN.md Part 1, the CLAUDE.md rules, and decisions 0002–0006. Decision 0002 (client-side wins, open RLS) was treated as settled. Findings that build on it are labelled "extension of 0002". Items the 2026-10-05 trim already handled are not reported again.

## Findings

### High

```
[High] src/hooks/useRealtimeRoom.ts:225-239 + src/components/game/RoomClient.tsx:406-416, 470-477 — The player's own game_players row is created by a single upsert with no retry. Every later marks and win write is an .update() that treats zero rows as success.
  Scenario: The game_started upsert fails once because of a network blip. The player sees one toast: "Stats may be missing". After that, every marks save matches 0 rows and reports no error, and so does the win write, so the player is never warned again. Other tabs' catch-up reads find no won row, so after about 20s (CATCH_UP_WINNER_GRACE_MS) staleWinnerIds removes the winner and the bingo announcement disappears. A refresh then restores with ownRow = null and inserts marks: [], and the whole board is gone. That breaks two invariants: "losing the whole board is not" tolerated, and neither is "a missed bingo announcement".
  Fix: Wrap the upsert in withRetry. Make the marks and win writes upserts, or add .select() and treat 0 rows as a failure to retry.  (verified)

[High] supabase/migrations/20260410000004_open_select_rls.sql + src/components/game/ProfileModal.tsx:85-89 — Every player's claim_code and browser_id can still be read with the public anon key. Carried over from the baseline; extension of 0002.
  Scenario: Anyone requests /rest/v1/players?select=claim_code, enters a friend's code in Profile, then clicks Claim, and becomes that friend, with their history and wins. PlayerProvider.tsx:71 also reads select('*').
  Fix: Serve players through a view that leaves out claim_code and browser_id, and do the claim lookup in a security-definer RPC. Move both keepalive pingers off `players` in the same change (see the Low under Process).  (verified)
```

- Library writes follow decision 0003. Owner-only writes check the row count through expectRows, and Add never evicts (0004).
- There are no XSS sinks, game colors resolve through fixed keys, the dev `?state=` harness is gated on NODE_ENV, and the mock Supabase binds to loopback only.
